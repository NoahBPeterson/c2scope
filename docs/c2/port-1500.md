# The tracing tools on cl 15.00 (Visual C++ 2008 SP1): c2.dll 15.00.30729.1

`c2trace` (`regs`, `scratch`, `il`, raw hooks), `regmap`, `c2sched`, `tsweep`, `helpersweep`, `rwsweep` and
`rasim` run against the cl 15.00 back end through `--c2 15.00` (or `C2_BUILD=15.00`), the same way as 13.10
(port-1310.md). 14.00 stays the default. This file records which binary was ported, how every address was
found, what differs from 14.00, what was checked and what was not.

Tags: **[C]** confirmed (read in the 15.00 code at the cited address, or seen in a 15.00 trace), **[I]** inferred.
Addresses are 15.00.30729.1 VAs at the preferred image base 0x51030000 unless a column says otherwise. The
image has a dynamic base and is relocated at run time under wine (seen at 0x7a260000 to 0x7b000000); the trace
DLL rebases every address, so table addresses are always the preferred ones. **[C]**

## 1. Summary

- One 15.00 x86 compiler is on this machine: **15.00.30729.01 (VS2008 SP1)**, the one spore-decomp compiles
  with. Its c2.dll has a public PDB on Microsoft's symbol server, so every function and global is located by
  **name**, not by matching. **[C]**
- `tests/run_tests.py` gives the same result on 15.00 as on 14.00: 14 of 14, with identical numbers. **[C]**
- **The Spillcosts priority formula is the same as in 14.00**: block weight 1 at /O1, 2^(loop depth) at /O2,
  a count ratio under PGO; the pressure factor P; `prio += blkcost·P·w` for referenced values and
  `prio −= P·w` for values live through; ChoosePhysReg adds `benefit·100` for a neighbour with one register
  left and takes the first register of eax ecx edx esi edi ebx ebp with a strictly lower weight (section 6).
- rasim needs no 15.00 parameter for register allocation: 0 mismatching priority terms in 2.2 million, every
  register predicted (section 7). The scheduler has one 15.00-only rule, which `c2sched.py --verify` now
  models through a table key (section 6.3).
- No GLOBREG, SYM, tuple, BB or DAGNODE offset the tools read has moved. What moved: every address, the
  pseudo-opcode numbers (+0x4b), a few FUNC and Module offsets the tools do not read, and the registers and
  stack slots the mid-function probes read from (15.00 functions keep an ebp frame) (sections 3.2, 4).
- LTCG: the entry-point patch loads the trace DLL in link.exe as well; `tools/c2ltcg.py` wraps it (section 8).
- What the optimiser in front of the allocator does differs (loop unrolling, more `lea`), so the same source
  can reach Color with different candidates on 15.00. That is not the allocator (section 6.4).

## 3. Symbols and how functions were located

`https://msdl.microsoft.com/download/symbols/c2.pdb/FDFABF3C1E0F4766A572C84FCA5FB787B/c2.pdb` returns the PDB
uncompressed: 1,051,648 bytes, sha256 `a510c6e087ed8ebf479f169eb92708d67ac36224609677dd481b8e03ba3f7563`, kept
in `work/pdb/15.00.30729.1/` (git-ignored). It is a stripped public PDB: 9618 publics, section contributions,
214 modules, no types. **[C]**

`uv run tools/pdbindex.py <c2.dll> --pdb … --out work/index/15.00.30729.1/c2.dll.csv` (the `--out` option is
new) gives 5080 named functions and 33 unnamed code contributions. Names are C++-decorated
(`?Color@@YIXPAUtagFUNC@@@Z`, `?Spillcosts@@YIXPAUtagFUNC@@W4GLOBREGLASS_ENUM@@PAUtagBV@@@Z`), where 14.00 has C
names (`@Color@4`). Every function the tools hook exists in 15.00 under the same base name. `tools/c2port.py`
was not needed. **[C]**

So that hook lists and `il --at` keep one spelling across builds:

- the table's `functions` are keyed by the 14.00 name (`@Color@4`) and carry the real 15.00 name in the fourth
  field; confidence is `pdb` for all of them;
- for any other function, `image.Image.func` accepts the 14.00 spelling when exactly one 15.00 function has
  that base name (`il --at @FgRemoveDuplicateArcs@4` and `--at '?FgRemoveDuplicateArcs@@YIXPAUtagFUNC@@@Z'`
  both work). **[C]**

## 6. Behaviour: 15.00 against 14.00

### 6.1 Spillcosts, Color, ChoosePhysReg

Read in 15.00 Spillcosts (510629e0) next to 14.00 (10b10420); the two are the same code with an ebp frame:

- **Block weight** (51062c0a..51062c96): `Speed` == 0 → w = 1; `PogoFlag` == 2 → count·10000/PogoMaxCount + 1 (1
  when either is 0); otherwise `w = 1 << byte [BB+0x17e]`. Traced: /O1 gives w = 1 in every block; a triple
  loop gives blocks of w 1, 2, 4, 8 in the same numbers as 14.00 (5, 4, 4, 1). **[C]**
- **P** (51063958..510639fd): the bit count of a per-block set built during the scan ([ebp−0x20]), plus the
  length of the list of globregs that died in the block, plus the live ones with fl6 & 0x10 (referenced). The
  same three sums, in the same order, as 14.00 10b113cb..10b1147e. **[C]**
- **End of block** (510639ff..51063a6c): `P·w` = P · [ebp−0x18]; a globreg that died gets
  `prio += blkcost·P·w` (51063a15); a live, referenced one the same (51063a4e); a live, unreferenced one
  `prio −= P·w`, under PGO `prio −= w` (51063a5c..51063a69). **[C]**
- Arithmetic census of the whole function (every `imul`, `shl`, scaled `lea`): the same seven multiplications in
  both builds. Callees: 14.00 has one `SbvTestBit` call, one `SbvAlloc` and one `getmem` more than 15.00
  (inlined or merged; no effect seen). **[C for the census, I for "no effect"]**
- **Order**: InsertInList (51063f00) has the same instructions as 14.00's; OrderGlobregs walks `GlobregHash`
  upward; InsertByBenefit and SpillOrDefer have the same instruction mix (no differing offset or constant). **[C]**
- **Color** (5105f880): calls the same functions the same number of times as 14.00; the pop loop tests
  `benefit <= 0` with the zero-benefit exception (one block, not an immediate, nrefs > 2, `Speed`), BetterToDefer
  unless fl5 & 4, uncolourable when avail is empty (5105fc9f..5105fd18). **[C]**
- **ChoosePhysReg** (51066f30): weights cleared (0x174 bytes); `+= count` for a neighbour's available PREFs;
  `+= benefit·100` for a neighbour with one register left (51067076 `imul eax,eax,0x64`); `−= count` for own PREFs
  (51067129); then the first register of `RegOrders[class]` with a strictly lower weight (510671b9 `jge` skips).
  Traced: `s` in fc.c gets `ebp:1200`. **[C]**
- **Scratch pass**: RegAssign (511288b0) takes a preference from the same seven copy-like opcodes and from

### 6.2 Where rasim and 15.00 disagree

- Priority terms and registers: nowhere.
- Colouring order: 2 of 587 pops in b25.c, 0 of 1899 in b100.c. Both misses are re-pops after a deferral in a
  pass where immediates and re-split values are queued together (`re-pop 301 is imm0 but the deferral model's
  #1 is v38`). 14.00 misses 2 of 315 on the same file in the same way. InsertByBenefit (51063f80) is the 14.00
  code: an immediate goes to the tail of the whole list, another value goes before the first deferred entry
  with a benefit not below its own, and never behind a deferred immediate. rasim orders the re-pops of a pass
  among themselves only; entries that InsertInList adds between two deferrals are not in that model. It is a
  model gap shared with 14.00, not a 15.00 rule, so nothing was parameterised. **[C for the code, I for the
  cause of these two pops]**
- Before the trace DLL's dereference limit was raised (port-1310.md), 15.00 showed "state divergences" for
  globregs with five or more PREFs (b25.c: 17, b100.c: 26; 14.00 has none because its b25 has no such globreg).
  With the rebuilt DLL there are none. **[C]**

### 6.3 Scheduler: one new rule

`c2sched.py --verify` on b25.c with the 14.00 model: height and static priority match on every node (1569 of
1569), the selection replay missed 6 of 1569 picks, each a `cmp`/`test` with the top priority that was not
picked. The cause is `SchmdShouldDelayCmp` (512378c0), called from SchSelectInstrs (511da2d6) and absent from
14.00 **[C]**:

- the node has exactly one successor (+0x26 == 1) and its instruction is `cmp` (0x2f) or `test` (0x33);
- one of its first two sources is a register;
- the successor is a `_jcc` (0xf); for `cmp` the jcc's type code (tuple +0xa & 0x1f) is one of 1, 2, 7, 8, 9, 10;
- the jcc still has another predecessor edge to wait for (+0x24 != 1).

Then the cmp is passed over in this pick. The effect is that a compare is issued last, next to its branch.
The table key `sched_delay_cmp` = [cmp, test, jcc opcodes] turns the rule on in `simulate_check`; event 2 logs
the instruction's kind/type word and the kind words of its first two sources for it. With it: 1569 of 1569
(b25.c) and 5079 of 5079 (b100.c). 14.00 stays at 1183 of 1183. **[C]**

Also: `SchmdHWT` is referenced from SchComputeStaticPriority, and only `OpSchedInfoP0` exists (the P4 and P5
cost tables are gone); neither changed a checked rule. **[C that they exist; I that nothing else follows]**

## 8. LTCG

With `/GL`, cl writes IL objects; `link /LTCG` loads c2.dll and runs the back end over all objects in one
process. The trace patch is in c2.dll's entry point (it runs on `DLL_PROCESS_ATTACH` in whichever process loads
the DLL) and loads `c2trace.dll` by bare name, which resolves in link.exe's own directory, the same `VC/Bin`.
So it works under the linker unchanged. **[C]** What differs in that mode:

- cl still loads c2.dll for a /GL compile (a log with zero events is written), so the trace must be taken
  from the **link** step. **[C]**
- there is no listing (`/FAsc` gives none under /GL), so anything needing the listing (`regmap`, tsweep's
  `ins()`) has nothing to align with; `scratch` offsets come from the IL's encoded lengths and are correct;
  (since docs/c2/ltcg.md: c2ltcg.py writes a listing disassembled from the linked image, so `regmap`, `tsweep`,
  `rwsweep` and `helpersweep` work through it on every build);
- functions are those the linker generates: after cross-module inlining, with custom register conventions for
  functions nothing outside reaches, in the linker's order.

`tools/c2ltcg.py` does the two steps and hands the log to the ordinary reports:

```sh
uv run tools/c2ltcg.py --c2 15.00 regs work/port1500/ltcg/a.c --with work/port1500/ltcg/b.c --export entry -- /GS-
uv run tools/c2ltcg.py --c2 15.00 scratch a.c --with b.c --export entry --func helper -- /GS-
uv run tools/c2ltcg.py --c2 15.00 il a.c --with b.c --export entry --func helper --at @Color@4
uv run tools/c2ltcg.py --c2 15.00 raw a.c --with b.c --export entry -H @Color@4=s1
```

Two-file test (a.c: `helper` with a loop calling `g`; b.c: `g` and `entry`, which calls `helper` twice)
**[C]**:

| build | what link.exe's c2 compiled | `regs` |
|---|---|---|
| 15.00 | `_g`, `_helper` (g inlined, loop unrolled), `_entry` (helper **not** inlined) | helper 21 pops, entry 4 pops (r → esi, n → edi, a → ebx) |
| 14.00 | `_g`, `_helper`, `_entry` with helper inlined twice | entry 21 pops |
| 13.10.3077 | the same shape as 14.00 | helper 7 pops, entry 21 pops |

For Spore this matters on the 13.10 side: its /GL + /LTCG code is the RenderWare 4 core (section 2), and
