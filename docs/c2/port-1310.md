# The tracing tools on cl 13.10 (Visual C++ .NET 2003): c2.dll 13.10.3077 and 13.10.3052

`c2trace` (`regs`, `scratch`, `il`), `regmap`, `c2sched`, `c2ltcg`, `tsweep`, `helpersweep`, `rwsweep` and `rasim`
run against the 13.10 back end as well as against 14.00.50727.762 (parity table: section 10). The build is a parameter; 14.00 stays the default and its code paths are
untouched. This file records which binaries were ported, how every address was found, what differs from 14.00,
what was checked and what was not.

Tags: **[C]** confirmed (read in the 13.10 code at the cited address, or seen in a 13.10 trace), **[I]** inferred.
Addresses are 13.10.3077 VAs (image base 0x10700000) unless a column says otherwise.

## 1. Summary

- Both 13.10 builds found on this machine are supported: **13.10.3077** and **13.10.3052**. The regression tests
  (`tests/run_tests.py`) give the same 18 of 18 results on 14.00, 13.10.3077 and 13.10.3052. **[C]**
- **13.10 weights loop bodies exactly as 14.00 does.** Block weight w = 2^(loop depth) at /O2, 1 at /O1, the
  pressure factor P and the live-through penalty −P·w are all there, in the same code shape (section 6). The
  open question in regalloc.md §9.6 and regalloc_cost.md §10 is answered: yes, same formula, with loop weighting.
- rasim needs no per-build parameter: priority terms, colouring order and (with the register-choice probes) the
  chosen registers are reproduced on 13.10 with the 14.00 model (section 7).
- No PDB exists for 3052 or 3077. Names come from the public PDB of the later 13.10.6030 (VS .NET 2003 SP1) c2.dll,
  carried over by code matching (section 3).
- x87 values: 13.10 allocates them in `FPColor`, outside Color's class loop, with its own costs (no pressure
  factor). `regs --all-classes --why` gives FPSpillcosts' per-block terms and the reason for every split, `--export`
  carries FPColor's passes and events, and rasim checks its priorities, list order and worthless drops
  (fpcolor.rs; 87 M&B functions: 2534 webs, 694 of 694 pops, 1490 of 1490 drops) and answers `need 'A>B'` for x87
  webs (section 12). Whether a popped web stays on the stack (FPCheckColorability, a stack-nesting test) is read
  from the trace, not predicted. Everything else in the parity table works on both builds.

## 3. Symbols and how functions were located

Microsoft's symbol server has no `c2.pdb` for 3052 or 3077 (404 for the RSDS keys above with age 1 and 2, as
`.pdb` and `.pd_`, and for the image keys). It **does** have the public PDB of the 13.10.6030 c2.dll:
`https://msdl.microsoft.com/download/symbols/c2.pdb/5360F7BDAFB54288A53F1FBE04D639112/c2.pdb` (3,124,224 bytes,
sha256 `5d9d851d…d940aa`, kept in `work/pdb/13.10.6030/`). It has 6703 publics with the same decorated names as
14.00 (`@Color@4`, `@Spillcosts@12`, ...). **[C]**

All three 13.10 images are BBT-optimised: basic blocks of one function are scattered over .text, functions have
no alignment and no single extent. The 6030 PDB therefore carries OMAP streams, and its publics are in the
pre-BBT address space. `tools/c2port.py names` translates them through OMAP_FROM_SRC. **[C]**

`tools/c2port.py match` then pairs functions of 6030 with functions of the target build:

1. Both images are explored by recursive descent from every call target (and exports, code pointers in data,
   jump tables), so a function is the set of its reachable instructions wherever the blocks lie.
2. Each instruction is reduced to its bytes with relocated dwords zeroed; branches keep only their class (jcc,
   jmp, call), because BBT inverts conditions and inserts or removes jumps. A function is the multiset of these.
3. `sig`: the multiset is identical and unique on both sides. `calls`: the best multiset similarity among the
   still unmatched callees or callers of an already matched pair (the call-graph position), iterated.

Result: of 3463 named 6030 functions, 3285 are placed in 3077 (2675 `sig`, 610 `calls`) and 3281 in 3052; 684
data symbols follow from relocated operands of instructions that are unique in a matched pair. The full maps are
`work/index/13.10.*/c2.dll.csv` (optional; any carried-over name can then be hooked or used with `il --at`).

For 3052 every address was also derived a second, independent way: the masked byte context around the 3077
address is searched in 3052 and must be unique. All 38 functions agree between the two routes. **[C]**

## 5. Tool changes

- `tools/c2build.py` (new): build selection. `C2_BUILD=13.10` in the environment, or `--c2 13.10` on the command
  line of any tool that imports it (removed from argv before the tool parses; exported to child processes).
  Aliases: `13.10` = `13.10.3077`, `3077`, `3052`, `14.00`.
- `tools/c2builds/13.10.3077.json`, `13.10.3052.json` (new): c2.dll hash, image base, cave addresses, tuple
  layout for the dumper, opcode names, the functions and probes above, and the hook lists (`regs`, `scratch`,
  `scratch_x`, `sched`, `il_spec`, `il_default`, `default`), plus `opsched` (cost table address, rows) and
  `regs_events` (the FPColor events of section 12).
- `tools/c2port.py` (new): `names` (PDB publics through OMAP), `match` (carry names to a PDB-less build), `table`
  (write the hooked functions into a build table, and the optional full index).
- `c2trace.py`: toolchain paths and cave constants come from the table when a build is selected; the trace config
  gets `set base|regname|opname|opcount|blk|len|mem` and `op <n> <name>` lines, which c2trace.dll now understands
  (defaults are the 14.00 values, so a 14.00 config is unchanged). A bare address or a listed probe can be hooked
  without a containing function row. `image.py` loads the selected build's c2.dll and index; `msvc.py` uses its
  toolchain directory; `c2regs.py`, `c2scratch.py`, `c2il.py`, `c2sched.py` take their hook lists through
  `c2build.hooks()`.
- 14.00 was re-checked with a c2trace.dll rebuilt from the changed source in a private copy of the traced
  toolchain: `regs` (with `--why`, `--block`), `scratch`, `il` and raw hooks print the same text as the installed
  DLL apart from heap addresses. The installed `work/toolchain/vs2005-trace` was not touched. **[C]**

## 6. Behaviour: 13.10 against 14.00

Read in 13.10 Spillcosts (10782473) and checked by traces:

- **Block weight** (10782433..1078245a): `_Speed` == 0 → w = 1; `_PogoFlag` == 2 → count·10000/max + 1;
  otherwise `w = 1 << byte [BB+0xa6]`. Traced: `sum` loop body w = 2; a doubly nested loop w = 4; the M&B
  function below w = 8 at depth 3; t1.c at /O1 w = 1 everywhere. **[C]**
- **End of block** (10782897..10783a80): P = distinct globregs referenced in the block; every referenced
  uncoloured globreg gets `prio += blkcost·P·w` (10782919, 10783a45), every one live through and unreferenced
  gets `prio −= P·w` (10783a7b; under PGO `−= w`, 107c21ce). **[C]** `regs --why` terms add up to the popped
  priority in every 13.10 trace taken (0 mismatches in over 160,000 terms).
- t1.c (`do { g(a); g(a); } while (gx);` then uses of b, c, d) gives a = 23, b = 21, c = d = 9 on 13.10.3077: the
  very numbers of regalloc.md §3.2 for 14.00, block by block. **[C]**
- **Order**: InsertInList 10782b26 sorts by prio descending (signed), then defOrd descending (unsigned), newcomer
  before an equal entry; OrderGlobregs walks hash buckets upward. defOrd is the per-instruction counter of
  RewriteAsGlobregs (1077fa99 increments, 1077fae3 stores), blocks forward, instructions backward. All as in
  14.00. **[C]**

  fl5 & 4, uncolourable when avail is empty. **[C]**
- **ChoosePhysReg** (107833f2): weights cleared, `+= count` for a neighbour's available PREFs, `+= benefit·100`
  for a neighbour with one register left (10784b48), `−= count` for own PREFs (1078c06b), then the first

  reset at function start and at opcode 0x2d3 (OPUSERSTATEMENT, 14.00's 0x303). The eA / eB pick sequences of
  the regression test are the same on both compilers. **[C]**
- Differences seen: none in the allocator's rules. The IL reaching it can differ (b25.c: 420 pops on 13.10, 430
  on 14.00), and RegSimpleAssign is one pass per function in 13.10 where 14.00 calls RegSimpleAssignBody once for

## 12. x87 values: `FPColor`

On 13.10 an x87 value never enters Color's class loop. Color calls `FPColor` (1071133c) when FUNC+0x8c has bit
0x10; 13.10 has no `X87*` (GFx to STx) functions at all. The rules (costs, order, worthless drops, the stack-nesting
colourability test, calls, the depth of 8) are in **x87.md section 11**, with addresses; the short form **[C]**:

1. `FPInitialRegPressure` 10710863 puts every x87 web live across a call into a split set (and makes a split point
   after an instruction where 8 temporaries are live).
2. `FPSpillcosts` 1071128c: prio = benefit = Σ cost·w over the web's references (def +2 float / +4 double, use 0
   float / 1 double, enterload −1 / −2, leave-store −2 / −4, an fld of a dying value 1 / 2) − w(S) for every edge
   B→S it is live out of B but not into S. No pressure factor P, no live-through term.
3. `FPAddToPriorityList` 107118e8: prio descending, defOrd descending, a newcomer before an equal entry (webs are
   inserted in ascending web number). `FPSpillWorthless` 10710b32 drops benefit ≤ 0, except (first call only)
   members of step 1's set.
4. The head is popped. `FPCheckColorability` 10712541 (LIFO nesting with the coloured webs) keeps it (colour =
   `&RegSym[0x1f]`; `FPUpdateRegisterPressure` 10711bad may then name webs to split for depth) or not (split set =
   {web}). A split round removes the set's members from the list (`FPRemoveSplitGlobregs` 1070e293), cuts them
   (`ColProcessSplitGlobregs` 1078b2aa), costs only the pieces and inserts them into the rest of the list.
5. `FPSinkIndirStores`, `FPRewriteAsReal` 10711502, `FPPeeps` 10756770 make the stack code.
